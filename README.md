# Neuro — MVP1

Система совместного анализа логов с LLM. Pure Python (FastAPI + SSR + HTMX).

## Запуск в PyCharm
1. Откройте папку `neuro-mvp1` как проект.
2. Создайте и активируйте виртуальное окружение:
   - Windows: `python -m venv .venv && .venv\Scripts\activate`
   - macOS/Linux: `python -m venv .venv && source .venv/bin/activate`
3. Установите зависимости: `pip install -r requirements.txt`
4. Скопируйте `.env.example` → `.env`, сгенерируйте `SECRET_KEY`:
   `openssl rand -hex 32`
5. Запустите: `uvicorn main:app --reload`
6. для запуска по локальной сети - `uvicorn main:app --host 0.0.0.0 --port 8000 --reload`
7. Откройте http://127.0.0.1:8000

## Где что лежит

 Проект разделен на логические блоки: настройки, база данных, обработчики страниц (роутеры), бизнес-логика (сервисы) и внешний вид (шаблоны).

### Корень проекта (настройки и запуск)
*   **`main.py`** — Точка входа. Здесь создается приложение, подключаются все страницы и создается админ по умолчанию.
*   **`config.py`** — Чтение настроек из файла `.env` (секретные ключи, лимиты файлов и т.д.).
*   **`database.py`** — Подключение к базе данных SQLite. Здесь же функция `get_db()`, которая выдает доступ к БД.
*   **`models.py`** — **Главный файл для структуры БД**. Здесь описаны все таблицы (Пользователи, Чаты, Сообщения, Настройки).
*   **`schemas.py`** — Правила валидации форм (какой длины должен быть пароль, сколько символов в сообщении и т.д.).
*   **`requirements.txt`** — Список библиотек для установки.

### Папка `routers/` (Обработчики адресов)
Здесь лежат файлы, которые отвечают на запросы браузера (открытие страниц, нажатие кнопок).
*   **`auth.py`** — Вход (`/login`) и выход (`/logout`).
*   **`chats.py`** — Вся работа с чатами: главная страница, создание, отправка сообщений, поиск, удаление. *(Самый большой файл)*.
*   **`files.py`** — Загрузка файлов в чат.
*   **`settings.py`** — Страница настроек API нейросети (доступна только админу).

### Папка `services/` (Бизнес-логика)
Здесь лежит «тяжелая» логика, которую роутеры просто вызывают.
*   **`auth_service.py`** — Проверка паролей, создание JWT-токенов, проверка сессий.
*   **`llm_service.py`** — **Работа с нейросетью**. Сборка промпта, отправка запроса, получение ответа.
*   **`file_service.py`** — Обработка файлов: проверка расширений, нарезка на куски (чанки) и сохранение в ChromaDB (векторная база для RAG).

### Папка `middleware/`
*   **`session_activity.py`** — Следит за тем, чтобы сессия пользователя продлевалась, пока он активно пользуется сайтом (чтобы не выкинуло через 30 минут).

### Папка `templates/` (HTML-страницы)
*   **`base.html`** — **Главный каркас**. В нем лежит сайдбар (боковое меню), шапка и подключение HTMX/Tailwind. Все остальные страницы вставляются внутрь него.
*   **`login.html`** — Страница входа.
*   **`index.html`** — Главная страница (заглушка, если нет чатов).
*   **`chat.html`** — Окно чата (лента сообщений и форма ввода).
*   **`settings.html`** — Форма настроек API для админа.
*   **`components/`** — Мелкие кусочки страниц:
    *   `chat_list.html` — список чатов в сайдбаре.
    *   `message.html` — отображение одного сообщения в ленте.
    *   `banner.html` — желтая плашка «Сервис недоступен».
    *   `modal_confirm.html` — всплывающее окно подтверждения удаления.

## 🤝 Инструкция по командной работе в GitHub

Чтобы мы не теряли код, не ломали рабочие функции и не мешали друг другу, мы работаем по следующим правилам. Пожалуйста, прочитайте их перед началом работы.

### Основные правила
1. Ветка `master` защищена. Никто не пушит в неё напрямую. Все изменения — только через Pull Request (PR).
2. Одна задача = одна ветка. Не делайте одну ветку на всю неделю.
3. Перед началом работы всегда обновляйте `master`.
4. Перед созданием PR обновляйте свою ветку из `master`, чтобы избежать конфликтов.
5. PR должен получить 1 одобрение (Approve) от коллеги.

---

### Пошаговый алгоритм (шпаргалка)

## Шаг 1. Начало новой задачи
Всегда начинайте с обновления главной ветки, чтобы взять за основу самый свежий код.

### 1. Переключаемся на master
git checkout master

### 2. Забираем свежие изменения с GitHub
git pull origin master

### 3. Создаем свою ветку (название на английском, без пробелов!)
Примеры: feature/export-chat, feature/notifications, feature/prompts-crud
git checkout -b feature/название-вашей-задачи


## Шаг 2. Работа над задачей
Пишите код, проверяйте его локально. Когда сделали логический кусок — сохраняйте его.

### Добавить все измененные файлы
git add .

### Сделать коммит с понятным сообщением
 Шаблон: feat: краткое описание / fix: краткое описание
git commit -m "feat: добавлен экспорт в txt"

### Отправить ветку на GitHub (делается ОДИН раз при первом пуше)
git push -u origin feature/название-вашей-задачи

### Все последующие пуши в эту же ветку — просто:
git push


## Шаг 3. Создание Pull Request (PR)
Когда задача готова (или вы хотите показать промежуточный результат):
1. Зайдите на GitHub в наш репозиторий.
2. Нажмите зеленую кнопку "Compare & pull request" (появится рядом с вашей веткой) или перейдите во вкладку Pull requests -> New pull request.
3. В поле base выберите `master`, в поле compare — вашу ветку.
4. Заполните Title и обязательно Description:
   * Что сделано: (список изменений)
   * Как проверить: (пошаговая инструкция для ревьюера)
5. Справа выберите Reviewer (того, кто будет проверять) и назначьте себя в Assignees.
6. Нажмите Create pull request.


#### Шаг 4. Что делать, если `master` ушел вперед (конфликты)
Если пока вы работали, кто-то уже влил свой код в `master`, перед мержем вашего PR нужно обновить вашу ветку. В терминале:

# Убедитесь, что вы в своей ветке
git checkout feature/название-вашей-задачи

# Заберите свежий master
git fetch origin
git merge origin/master

Если появился конфликт (Git пишет CONFLICT):
1. Откройте файл с конфликтом.
2. Найдите маркеры <<<<<<< HEAD, =======, >>>>>>> origin/master.
3. Оставьте нужный код (обычно нужно оставить оба варианта), удалите сами маркеры.
4. Сохраните файл, затем в терминале:

git add .
git commit -m "merge: разрешен конфликт"
git push

PR на GitHub обновится автоматически, конфликт исчезнет.


#### Шаг 5. Ревью и слияние (Мерж)
* Автор PR: Ждет, пока назначенный ревьюер проверит код.
* Ревьюер: Заходит в PR -> вкладка Files changed -> читает код. Если всё ок, нажимает Review changes -> Approve. Если есть замечания — Request changes (тогда автор их исправляет и снова пушит в ту же ветку).
* После одобрения: Нажмите зеленую кнопку Merge pull request -> Confirm merge.
* После мержа: GitHub предложит удалить ветку — нажмите Delete branch (история коммитов останется в `master`, а ветка больше не нужна).


#### Шаг 6. После слияния
Вернитесь на локальный компьютер и обновите свой `master`, чтобы забрать общий код:

# Переключитесь на master
git checkout master

# Заберите изменения
git pull origin master

# Удалите локальную ветку (если она больше не нужна)
git branch -d feature/название-вашей-задачи

### 💡 Полезные советы
* Названия веток: только латиница и дефисы. Пример: feature/export-chat, а не "Егор экспорт".
* Сообщения коммитов: пишите так, чтобы через месяц было понятно, что изменилось. Плохо: fix, update. Хорошо: "fix: исправлен счетчик уведомлений".
* Если забыли создать ветку и начали править код в `master`: не паникуйте. Просто выполните `git checkout -b feature/название-задачи` — все незакоммиченные изменения перейдут в новую ветку.
* Никогда не делайте `git push --force`, если вы не уверены в своих действиях. Это может перезаписать чужой код.
